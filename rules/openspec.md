# OpenSpec
> A behaviour change goes through an OpenSpec change before code; the coordinator only dispatches (openspec-apply-orchestrator skill).

- If the project uses OpenSpec (it has an `openspec/` directory) and the main
  session delegates change work to subagents, load the
  `openspec-apply-orchestrator` skill first
  (`~/.claude/skills/openspec-apply-orchestrator/SKILL.md`). It keeps the
  coordinator a thin dispatcher. Where a project runs leads (ALIX: `alix-lead`,
  `bin/route`), the lead loads it and the main session only routes.


How a change runs (each project binds these to its own commands, skills and
agents in its file):

- A feature or a change of behaviour goes through an OpenSpec change before
  code is written. A bug fix, a wording change, or a refactor that changes
  no behaviour needs none; it still happens in a worktree and ends with the
  full gate.
- `openspec/specs/` is the current source of truth, one folder per
  capability; `openspec/changes/` holds proposed changes (proposal, design,
  tasks, spec deltas). The `/opsx:*` commands and `openspec-*` skills are
  generated by `openspec update` and overwritten on every update: never edit
  them; project rules go in the project's own skills and agents.
- Stages: research and plan, spec review and fix, apply, apply review and
  fix, archive. Each stage ends by starting its successor: planning runs the
  spec review before the plan is presented, and every apply ends with the
  apply-review gate.
- Revising a change means sweeping every place the old wording lives:
  proposal, design, tasks, all spec deltas, and the docs the change wrote
  outside `openspec/changes/`. Finish with `git grep -n '<old term>'`
  returning nothing, then `openspec validate <change> --strict`.
- Workers run in worktrees branched from the change branch, one fresh worker
  per group of tasks. A worker reads only its group brief, runs the group's
  tasks in order in one context, loops on the quiet check within its budgets
  (three failed rounds, a hang timeout, 40 minutes), fixes a red check in the
  same run, and commits when the check passes. The coordinator runs the one
  full gate per wave after merging. A blocker outside a worker's files is
  reported, not debugged. Debug prints are allowed while diagnosing, but each
  is removed and reported as a missing diagnostic, and becomes something the
  code shows: a field of state, an event, or a sharper error.
- In every stage the coordinator only dispatches: it reads ids, progress
  lines, and hand-backs of at most 10 lines, never the artifacts, code, or
  full test output; the typed agents write. Reports go to the session
  scratchpad.
