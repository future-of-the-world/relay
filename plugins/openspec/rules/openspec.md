# OpenSpec
> Where a project turns spec steps on, a behaviour change gets an OpenSpec change before code; the steps run inside relay's change cycle.

This project has OpenSpec spec steps turned on (`[specs] method = "openspec"` in
`.claude/kit.toml`). They are extra steps around relay's one change cycle (the
delegate skill, "Review loop"); the build and the fixes are the cycle's own.

- A feature or a change of behaviour goes through an OpenSpec change before
  code is written. A bug fix, a wording change, or a refactor that changes no
  behaviour needs none; it still happens in a worktree and ends with the
  full gate.
- `openspec/specs/` is the current source of truth, one folder per
  capability; `openspec/changes/` holds proposed changes (proposal, design,
  tasks, spec deltas). The `/opsx:*` commands and `openspec-*` skills are
  generated by `openspec update` and overwritten on every update: never edit
  them; project rules go in the project's own `.claude/kit/<stage>.md`.
- Revising a change means sweeping every place the old wording lives:
  proposal, design, tasks, all spec deltas, and the docs the change wrote
  outside `openspec/changes/`. Finish with `git grep -n '<old term>'`
  returning nothing, then `openspec validate <change> --strict`.
- The spec steps run at the steps of the change cycle listed below this rule.
  To turn them off, run `relay setup <dir> --specs none`; the `openspec/`
  folder is then left as the project's docs.
